## 9. Sequencing note

The four PRs MUST land in the order shown in §3. Each PR is atomic: do not split a PR's commit. If a PR tips over 600 changed lines, the design's density risk (design §16.1, `proposal.md` §9.1) is resolved by deferring the indicated tasks to PR 4 — never by splitting the PR in two mid-stream. Specifically:

- PR 1 ships the rectangular `useEffectMarkers` stub intentionally (T1.10). Wall-aware BFS lands in PR 2 (T2.14).

- PR 3's `tickRoundInTx` is intentionally **not** exported as a standalone use case; the only legal caller is `applyOp` (proposal §9.3, design §16.3). An inline comment at the top of `tickRoundInTx` makes the contract explicit.
- PR 4's `marker bloqueado por muro` vignette (T4.5) is the only place the blocked-anchor visual is finalised; PR 2 ships a fallback (empty footprint, no vignette) so the wall-aware BFS is testable in isolation.

If a PR's diff is unexpectedly small (< 350 changed lines) the implementation MAY pull forward a clearly-scoped PR 4 polish task (e.g. the duplicate-label warning) without re-issuing the plan; this is an optimisation, not a change of order.
